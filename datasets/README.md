# CAD 平面图理解与矢量标注赛规则

## 1. 赛事任务

参赛者输入一张建筑平面图 PNG，识别图中的门、窗、家具、墙体等类别，并输出带有几何位置、语义类别和实例编号的矢量图元 JSON。

## 2. 数据集介绍

### 2.1 官网数据集

CAD 是面向建筑平面图理解研究的数据集，官网发布版本包含 **6000 张真实建筑 CAD 图纸**。图纸以 SVG 矢量形式提供，并带有逐图元语义标注；同时提供栅格化 PNG 及可视化材料。任务覆盖两种标注：

- **Thing（可数实例）**：例如一扇门、一张桌子。每个独立对象有自己的实例编号。
- **Stuff（不可数区域/类别）**：例如墙、窗帘墙、栏杆。每个独立对象有自己的实例编号。

### 2.2 下载官方原始数据

官网提供以下下载入口：

| 官方数据包 | 数据量 |
|---|---|
| train_final（训练集） | 4000 |
| test_final（测试集） | 1000 |
| dev_final（验证集） | 1000 |

下载后解压，先检查文件名是否一一对应。官方训练集和测试集数据包包含原始 SVG和PNG，验证集中包含原始PNG；

解压后本地数据根目录：

```text
datasets
├── train_final/
│   ├── <id>.png
│   └── <id>.svg
├── test_final/
│   ├── <id>.png
│   └── <id>.svg
└── dev_final/
    └── <id>.png
```

### 2.3 许可与使用

官网注明标注和网站采用 **CC BY-NC 4.0**；参赛者应遵守该许可及原图权利人的要求，仅在允许的非商业研究/竞赛范围内使用；公开模型、样例或二次数据时，应注明来源并确认有权再分发。不要将原始图纸用于商业用途或擅自公开传播。

## 4. 预测 JSON 格式

### 4.1 文件与编码

每张 `dev_final/<id>.png` 对应一个 UTF-8 JSON：`results/<id>.json`。`<id>` 必须与 PNG 的五位文件名完全一致。一个 JSON 表示一张图中的所有预测图元。`results/` 目录只放预测 JSON，不放 PNG、训练标签或映射表；

建议目录：

```text
队伍编号_submission.zip
└── results/
    ├── sKThF.json
    ├── r9BMw.json
    └── ... 共 1000 个 JSON
```

### 4.2 字段定义

以下 12 个字段对应的 JSON。图元数组中下标 `i` 表示同一个图元，因此各图元字段长度必须一致。

| 字段 | 类型/形状 | 含义 |
|---|---|---|
| `commands` | 整数数组，长度 N | 图元类型：`0=Line`、`1=Arc`、`2=circle`、`3=ellipse`。当前脚本从 path 的首段类型推断 `Line/Arc`，并直接解析 `<circle>`、`<ellipse>`；其它 path 首段类型当前不受支持。 |
| `args` | N×8 浮点数组 | 每个图元的 4 个二维采样点，按 `[x1,y1,x2,y2,x3,y3,x4,y4]` 展平；坐标单位与源图 SVG `viewBox` 一致。 |
| `lengths` | N 浮点数组 | 图元长度：path 长度、圆周长或椭圆近似周长。单位同 SVG 坐标。 |
| `semanticIds` | N 整数数组 | 每个图元的语义类别，使用本规则中的 JSON ID `0–34`；`35` 为背景/忽略。 |
| `instanceIds` | N 整数数组 | Thing 对象的实例 ID；同一对象的所有图元使用相同非负整数，不同对象不得共用；Stuff 或忽略图元使用 `-1`。实例 ID 只需在单张图内唯一。 |
| `width` | 正整数 | SVG `viewBox` 的宽度（代码会转成整数）。 |
| `height` | 正整数 | SVG `viewBox` 的高度（代码会转成整数）。 |
| `obj_cts` | M×4 数组 | 每个 Thing 实例的中心与实例号，形如 `[center_x, center_y, 0, instance_id]`。当前解析器按实例图元采样坐标的轴对齐包围盒中心计算。 |
| `boxes` | M×5 数组 | 与 `obj_cts` 同序的实例框，形如 `[x_min,y_min,x_max,y_max,semantic_id]`；框由该实例所有图元采样点的极值计算。 |
| `rgb` | N×3 整数数组 | 图元描边颜色 `[R,G,B]`，每通道 0–255。 |
| `layerIds` | N 整数数组 | SVG 遍历到的 `<g>` 层序号；从 1 开始。纯 PNG 预测没有源层级时，可统一填 `1`。 |
| `widths` | N 浮点数组 | 描边宽度 `stroke-width`。 |

`N` 是预测图元数；`M` 是 Thing 实例数。`obj_cts` 和 `boxes` 不包含 Stuff 的汇总框。预测 JSON 中这两个字段应根据 `instanceIds` 和 `args` 生成，不能用全图框代替实例框。若 JSON 供主办方按预测图元计算指标，应保留所有字段且相互一致。

### 4.4 校验要求

- JSON 必须能被标准 JSON 解析器读取；禁止 NaN、Infinity、字符串数字和注释。
- `len(commands) == len(args) == len(lengths) == len(semanticIds) == len(instanceIds) == len(rgb) == len(layerIds) == len(widths)`。
- 每个 `args[i]` 恰好 8 个有限数值；每个 `rgb[i]` 恰好 3 个 0–255 整数。
- `commands[i]` 只能是 `0、1、2、3`；类别只能是 `0–35`；实例号为整数且不小于 `-1`。
- 对类别 `0–29` 的 Thing 图元，实例号应为非负值；同一预测对象的图元类别必须一致。类别 `30–34` 的 Stuff 图元按约定使用 `-1`。
- `width`、`height` 表示 JSON 坐标系的宽高。
- `obj_cts` 与 `boxes` 行数相同，并且每行的实例号/类别和图元列表一致。推荐由主办方校验器重算并核对。
- 1000 张输入 PNG 必须各有一个同名 JSON；缺文件、重复 ID 或多余文件按无效提交处理。

## 5. 训练数据解析原理

训练数据中的 SVG 已带图元标注。下面的独立脚本读取 SVG `viewBox`，将 `<path>`、`<circle>`、`<ellipse>` 转为第 4 节规定的图元数组，并按实例号汇总 `obj_cts` 和 `boxes`。数组下标 `i` 指同一个图元。SVG 的语义 ID 为 1–35，写入 JSON 时减 1；缺少语义属性时用忽略值 35，缺少实例属性时用 -1。实例号原样保留，不重新编号。

本次数据中的标签属性名为 `semanticId` 和 `instanceId`；仅有 PNG 的 `dev_final` 不适用此转换脚本，提交预测须运行参赛队自己的图像推理程序。

## 6. 提交材料

提交一个 ZIP，命名为 `队伍编号_submission.zip`，内部至少包含：

- `results/`：1000 个预测 JSON，文件名与 `dev_final` PNG 一一对应。
- `README.md`：队伍名称/编号、模型说明、运行环境、完整推理命令、预测时间及随机种子。
- `requirements.txt` 或 `environment.yml`：可复现的依赖版本。
- `infer.py` 及必要的自编代码；若评测平台要求容器，可改交 Dockerfile/镜像说明。
- `weights/`：必要的模型权重（需跑通）；否则按竞赛平台指引提交。

不得在提交中包含测试真值、其他队伍数据、恶意代码或要求访问外部网络的评测逻辑。最终由赛事平台确认究竟采用提交代码和权重后由平台复跑；

## 7. 评分指标与公平性

本赛事采用 **PQ、SQ、RQ** 作为评分指标。三项指标共同评估全景实例结果：`PQ = SQ × RQ`；SQ 衡量已匹配实例的分割质量，RQ 衡量实例识别质量，综合反映正确匹配、误检和漏检。将 PQ 作为主要排名指标，同时公布 SQ 和 RQ 作为辅助结果。评测过程中固定代码版本、配置、随机种子、依赖和运行硬件，避免环境差异影响结果。

为了公平性，本次评测会固定从dev_final数据集中随机抽取数据进行评测，评测数据不会对外公开。
